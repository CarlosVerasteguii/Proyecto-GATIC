# GATIC 30-60-90 Roadmap Without Rework

- Status: active
- Created at: `2026-04-02T20:35:16-06:00`

## Objective

Turn the audit findings into an execution roadmap that professionalizes GATIC without creating avoidable rework.

The main constraint is explicit:

- Do not ask for a 30-day change that is likely to be invalidated by a 60-day or 90-day refactor.

This roadmap is therefore sequenced by stability:

1. First stabilize cross-cutting rules.
2. Then extract complexity out of hotspots behind stable boundaries.
3. Only after that, formalize structure that has already proved useful.

## Why This Sequence Avoids Rework

Rework usually appears when a team does one of these too early:

- introduces architecture before knowing the stable boundaries
- splits files before defining the contracts those files should obey
- modularizes folders while the logic is still unstable
- redesigns UI structure before the backend behavior has stabilized
- upgrades authorization complexity before the permission model is mature

This roadmap avoids that by separating:

- stable rules
- safe extractions
- late formalization

## Phase Summary

| Phase | Goal | Type of work | Rework risk |
|---|---|---|---|
| 30 days | stabilize standards and contracts | transversal hardening | low |
| 60 days | extract complexity from hotspots | internal structural refactor | medium-low |
| 90 days | formalize only what already proved stable | targeted architecture hardening | low |

## Phase 1: 30 Days

## Goal

Make the codebase safer to evolve before touching the large hotspots.

This phase is about rules that will still be correct in 90 days.

## Workstreams

### 1. Standardize unexpected error handling

Target:

- `gatic/app/Support/Errors/ErrorReporter.php`
- `gatic/app/Livewire/PendingTasks/PendingTaskShow.php`
- `gatic/app/Actions/PendingTasks/FinalizePendingTask.php`

What to do:

- route all unexpected errors through `ErrorReporter`
- remove manual `error_id` generation outside the standard path
- ensure critical flows persist and log failures consistently

Why this is safe now:

- this is a transversal rule, not an architectural bet
- later refactors will reuse the same error contract

### 2. Standardize audit recording

Target:

- `gatic/app/Support/Audit/AuditRecorder.php`
- `gatic/app/Jobs/RecordAuditLog.php`
- `gatic/app/Livewire/Admin/Settings/SettingsForm.php`

What to do:

- enforce one audit path
- remove direct `AuditLog::create()` style bypasses where they exist

Why this is safe now:

- audit consistency becomes a platform rule
- later refactors should call the same recorder, not replace it

### 3. Define and lock internal contracts before extraction

Target domains:

- Pending tasks
- Dashboard metrics
- Timeline / recent activity

What to define:

- input/output contracts for builders and actions
- which classes are orchestration only
- which classes own domain rules
- which classes are read-only projections

Why this is safe now:

- if contracts are defined first, extraction later does not become guesswork

### 4. Add unit tests to stable logic

Priority candidates:

- `gatic/app/Support/Assets/AssetStatusTransitions.php`
- `gatic/app/Actions/Search/SearchInventory.php`
- `gatic/app/Support/Timeline/TimelineBuilder.php`
- `gatic/app/Support/Dashboard/RecentActivityBuilder.php`

What to do:

- add fast tests around pure rules and deterministic builders
- reduce dependence on giant feature tests for internal logic verification

Why this is safe now:

- tests for pure logic do not become obsolete if the outer UI changes

### 5. Harden data integrity where the vocabulary is already closed

Target:

- `gatic/database/migrations/*assets*`
- `gatic/database/migrations/*users*`
- `gatic/database/migrations/*pending_task*`

What to do:

- review `role`, `status`, and other closed-value fields
- add missing indexes and constraints where the domain is already stable

Why this is safe now:

- data integrity is a foundation layer
- later refactors should rely on stronger constraints, not undo them

## Deliverables by Day 30

- one standard for unexpected errors
- one standard for audit writes
- documented internal contracts for pending tasks, dashboard, and event feed
- new unit tests for core logic classes
- a first pass of schema hardening for stable vocabularies

## Explicit Non-Goals for Day 30

- do not split `PendingTaskShow` yet
- do not split dashboard structure yet

## Phase 2: 60 Days

## Goal

Move complexity out of the largest hotspots without changing the external behavior of the application.

This is the extraction phase, not the redesign phase.

## Workstreams

### 1. Break down `PendingTaskShow` by responsibility

Target:

- `gatic/app/Livewire/PendingTasks/PendingTaskShow.php`
- `gatic/resources/views/livewire/pending-tasks/pending-task-show.blade.php`

Recommended split:

- lock/session coordinator
- line editor behavior
- quick capture processing path
- finalize/admin override path

Guardrail:

- keep the current route and outer entry point stable while the internals are split

Why this avoids rework:

- the user-facing entry point stays intact
- only internal ownership changes

### 2. Extract dashboard read services

Target:

- `gatic/app/Livewire/Dashboard/DashboardMetrics.php`
- `gatic/resources/views/livewire/dashboard/dashboard-metrics.blade.php`
- `gatic/resources/js/pages/dashboard.js`

Recommended split:

- metrics snapshot service
- critical queue service
- inventory value projection
- recent activity provider
- chart data builder

Guardrail:

- do not redesign the whole dashboard UX in the same step

### 3. Consolidate event feed logic

Target:

- `gatic/app/Support/Timeline/TimelineBuilder.php`
- `gatic/app/Support/Dashboard/RecentActivityBuilder.php`

What to do:

- create one shared event projection model
- derive timeline and dashboard views from that shared source

Why this avoids rework:

- if done after contracts are defined, the shared model becomes reusable instead of speculative

### 4. Split undo logic by strategy

Target:

- `gatic/app/Actions/Movements/Undo/UndoMovementByToken.php`

What to do:

- keep a small coordinator
- move each undo variant behind a dedicated strategy or action

Why this avoids rework:

- public flow stays the same
- internal branching complexity is reduced without altering the product workflow

### 5. Refactor giant feature tests into scenario-based suites

Target:

- `gatic/tests/Feature/Inventory/AssetsTest.php`
- `gatic/tests/Feature/Inventory/ProductsTest.php`
- `gatic/tests/Feature/DashboardMetricsTest.php`

What to do:

- split by behavior area
- reduce test files that validate too many concerns at once

Why this avoids rework:

- test decomposition supports later safe refactors instead of forcing them

## Deliverables by Day 60

- `PendingTaskShow` internally decomposed
- dashboard logic extracted to focused read services
- timeline and recent activity built on a shared event model
- undo flow split by strategy
- oversized feature tests reduced into smaller suites

## Explicit Non-Goals for Day 60

- do not migrate the app to a full module architecture yet
- do not rebuild the entire UX of pending tasks and dashboard yet
- do not introduce enterprise permission DSLs or global helpers

## Done Criteria for Day 60

- hotspot files shrink materially
- orchestration and domain rules are no longer mixed in the same large classes
- read-heavy concerns are visibly separated from write/transactional concerns
- core flows preserve current behavior

## Phase 3: 90 Days

## Goal

Formalize only the structure that has already demonstrated value after the earlier extractions.

This phase should consolidate, not destabilize.

## Workstreams

### 1. Introduce targeted authorization refinement

Target:

- `gatic/app/Providers/AuthServiceProvider.php`
- resource-specific flows such as attachments, pending tasks, settings, undo, and admin views

What to do:

- add policies or resource authorization objects where coarse gates are no longer enough

Why this belongs in 90 days:

- authorization refinement should follow stable flow boundaries, not precede them

### 2. Formalize route and domain boundaries if growth justifies it

Target:

- `gatic/routes/web.php`

What to do:

- split route definitions by domain only if the extractions from day 60 are already stable

Why this belongs in 90 days:

- route modularization too early is mostly cosmetic
- route modularization later becomes a reflection of real ownership

### 3. Standardize reusable Livewire interaction patterns

Target:

- `gatic/app/Livewire/Ui/*Combobox.php`

What to do:

- extract a shared pattern for repeated selector/search behavior
- document when to extend the pattern and when not to

Why this belongs in 90 days:

- the shared abstraction should be derived from stable similarities, not guessed in advance

### 4. Add governance guardrails to CI

Target:

- `.github/workflows/ci.yml`

What to do:

- add checks for complexity, file-size thresholds, or agreed architecture guardrails

Why this belongs in 90 days:

- guardrails should enforce a mature convention, not freeze an unstable one

### 5. Document domain conventions

Target domains:

- Pending tasks
- Inventory
- Dashboard
- Attachments
- Settings

What to do:

- document ownership, extension points, and anti-patterns

Why this belongs in 90 days:

- documentation is much stronger once the new structure has been tested in real work

## Deliverables by Day 90

- targeted authorization refinement in sensitive resources
- route/domain split only where justified
- standardized reusable Livewire interaction patterns
- CI guardrails for structural health
- domain-level engineering conventions

## Done Criteria for Day 90

- new features can be added without growing the same old hotspots
- permission logic is more resource-aware
- route and domain structure reflect real ownership
- CI can detect at least part of the structural drift that caused the original audit findings

## Anti-Rework Rules

These rules should be followed across all three phases.

### Rule 1

Do not change public entry points unless there is a user-facing requirement.

Example:

- keep the same route and component entry while splitting internals

### Rule 2

Prefer extraction over relocation.

This means:

- move logic into smaller dedicated classes
- do not reshuffle directories just to "look cleaner"

### Rule 3

Do not create shared abstractions until at least two stable use cases need them.

This especially applies to:

- Livewire UI patterns
- authorization helpers
- module conventions

### Rule 4

Put standards before structure.

This means:

- error handling
- audit handling
- data integrity
- tests

all come before large-scale refactor moves.

### Rule 5

Do not import enterprise complexity from Ingenia unless GATIC already has the same pressure.

Examples of things to avoid too early:

- full permission DSL
- helper-heavy authorization layers
- ecosystem-style module architecture
- infra complexity that does not solve a present bottleneck

## Decision Filter

Before approving a change, ask:

1. Is this a stable transversal rule that will still be valid in 90 days?
2. Is this an internal extraction that preserves behavior?
3. Is this a late formalization of something already proven?
4. Or is this a speculative architecture move?

If the answer is "speculative architecture move", it should probably not happen yet.

## Recommended Execution Order

1. Errors
2. Audit
3. Tests for stable logic
4. Data integrity hardening
5. Contract definition
6. Pending tasks extraction
7. Dashboard extraction
8. Event feed consolidation
9. Undo split
10. Authorization refinement
11. Route/domain formalization
12. CI guardrails

## Final Note

The roadmap is intentionally conservative.

Its purpose is not to maximize architectural ambition.
Its purpose is to remove the current bottlenecks in a sequence that remains valid three months later.
